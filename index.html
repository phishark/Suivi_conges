Attribution
Le solde reporté est calculé automatiquement à partir de l'historique (seul le CAS se reporte d'une année sur l'autre, période du 1ᵉʳ juin au 31 mai ; le CP ne se reporte pas). Vous pouvez corriger le CAS manuellement ici — par exemple après un ajustement RH — pour l'année uniquement ; les années suivantes se recalculent à partir de cette correction. CP, RTT1 et RTT2 sont remis à zéro chaque période (non reportables).

Vacances scolaires

Le calendrier utilise par défaut les dates de la zone B intégrées à l'application. Vous pouvez les remplacer par un fichier JSON personnalisé (autre zone, ou dates mises à jour) — soit un tableau de périodes, soit un objet {zone, periods}. Ce choix est enregistré avec le reste de votre configuration : il se synchronise donc automatiquement sur vos autres appareils si Supabase est configuré, et il est inclus dans l'export/import JSON. Exemple :
[{"start":"2026-10-17","end":"2026-11-02","label":"Vac. Toussaint"}, …]

Synchronisation Supabase

Connectez un projet Supabase gratuit pour synchroniser vos congés entre plusieurs appareils (ordinateur, iPhone…). Vos données restent aussi enregistrées localement dans ce navigateur.

Configuration requise côté Supabase (à faire une seule fois)

Dans votre projet Supabase → SQL Editor, exécutez une fois :

create table if not exists conges_sync (
  sync_id text primary key,
  days jsonb not null default '{}'::jsonb,
  config jsonb not null default '{}'::jsonb,
  updated_at timestamptz not null default now()
);

alter table conges_sync enable row level security;

create policy "acces via sync_id"
  on conges_sync for all
  using (true)
  with check (true);

Puis récupérez l'URL et la clé « anon public » dans Project Settings → API, et collez-les ci-dessus. ⚠️ Cette configuration simplifiée n'utilise pas de compte : toute personne connaissant votre Sync ID et votre clé peut lire/modifier ces données. Choisissez un Sync ID long et ne le partagez pas.
